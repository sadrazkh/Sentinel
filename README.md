# Sentinel — پرتال اختصاصی مشتریان

پرتالی برای مشتریان فعال سرویس، که در آن هر کاربر فقط به برنامه‌هایی دسترسی دارد که
اشتراک یا مجوز اختصاصی معتبر برای آن‌ها داشته باشد.

ASP.NET Core 10 · Entity Framework Core 10 · Razor Views · Vue 3 به‌صورت جزیره‌ای per-page
· PostgreSQL / SQL Server / SQLite

## معماری

```
src/
  Sentinel.Domain          موجودیت‌ها، enumها و قواعد خالص دامنه. بدون EF Core و ASP.NET Core.
  Sentinel.Application     قراردادها (ISentinelDbContext)، سرویس‌های دامنه، DTOها، Query Serviceها.
  Sentinel.Infrastructure  DbContext، پیکربندی موجودیت‌ها، Migration، Seed، پیاده‌سازی سرویس‌ها.
  Sentinel.Web             MVC، Razor Views، میان‌افزارهای امنیتی، Identity، Vue islands.
tests/
  Sentinel.UnitTests        منطق خالص (قواعد دسترسی، Audit metadata).
  Sentinel.IntegrationTests کل اپلیکیشن روی SQLite، بدون هیچ mock در مسیر احراز هویت.
```

### مدل دسترسی

دو موتور تصمیم‌گیری، هر دو تابع خالص، هر دو کاملاً unit-test شده:

- **`MembershipStatusResolver`** — وضعیت مؤثر عضویت را از روی تاریخ‌ها محاسبه می‌کند.
  `MembershipStatus` هرگز در دیتابیس ذخیره نمی‌شود؛ یک ستون «Expired» به یک job زمان‌بندی‌شده
  نیاز داشت و بین دو اجرا بی‌صدا اشتباه می‌بود.
- **`AccessRuleEvaluator`** — پاسخ «آیا این کاربر اجازهٔ باز کردن این برنامه را دارد؟».

ترتیب قوانین در `AccessRuleEvaluator` معنادار است:

1. **حساب** — غیرفعال یا مسدود؟ هیچ‌چیز دیگری بررسی نمی‌شود.
2. **برنامه** — غیرفعال یا منتشرنشده؟ برای همه بسته است، حتی دارندهٔ دسترسی اختصاصی.
3. **دسترسی اختصاصی معتبر** → مجاز. این دقیقاً کارکرد Entitlement است: یک ترتیب فردی که به
   زندهبودن اشتراک وابسته نیست و سطح عضویت را هم دور می‌زند.
4. برنامه‌های `RequiresExplicitEntitlement` همین‌جا متوقف می‌شوند؛ عضویت به‌تنهایی بازشان نمی‌کند.
5. در غیر این صورت **عضویت** تصمیم می‌گیرد: معتبر بودن، سپس `MinimumTier`.

`IAccessDecisionService` فقط ورودی‌ها را از دیتابیس جمع می‌کند و به Evaluator می‌دهد. همان یک
تابع، هم فهرست برنامه‌ها و هم endpoint اجرا را تغذیه می‌کند — اگر فهرست، دسترسی را جور دیگری
حساب می‌کرد، دیر یا زود با endpoint اختلاف پیدا می‌کرد و همان اختلاف، باگ امنیتی می‌شد.

### مدل عمومی محصول

`Product` جدولِ مشترک همهٔ محصول‌هاست و هیچ ستون مخصوص یک نوع محصول ندارد. آنچه بین محصول‌ها
فرق می‌کند در `ProductCapability` بیان می‌شود — یک bitmask از `[Flags]`، نه `switch` روی
`ProductType`:

```
Purchasable  Renewable  Downloadable  Launchable  HasDocumentation
HasConfigurations  HasUsageTracking  HasPlans  BetaAccess  RequiresActiveSubscription
```

`ProductType` فقط برای نمایش است. هر چیزی که رفتار را تعیین می‌کند از capability خوانده
می‌شود، بنابراین افزودن یک محصول با مکانیک کاملاً متفاوت به ستون جدید در این جدول نیاز ندارد و
سیاست هر ماژول هم به کاتالوگ مشترک نشت نمی‌کند.

`ProductAccessRules` یک لایهٔ **نمایشی** روی `AccessRuleEvaluator` است، نه جایگزین آن:
Evaluator همان یک پاسخ امنیتی را می‌دهد و endpoint اجرا هم همان را اجرا می‌کند؛ این لایه فقط
تصمیم می‌گیرد کارت چه برچسبی بگیرد و کدام یک دکمه را جلو بیندازد. چون پاسخ امنیتی دست‌نخورده
زیرش می‌ماند، افزودن یک call-to-action تازه هرگز نمی‌تواند به‌طور تصادفی دسترسی را گسترده کند.

**اجرای برنامه هرگز از سمت کلاینت نیست.** آدرس مقصد اصلاً به مرورگر فرستاده نمی‌شود؛ کارت فقط
به `/apps/{key}/open` لینک می‌دهد، سرور دوباره تصمیم می‌گیرد، URL را دوباره اعتبارسنجی می‌کند،
رویداد را ثبت می‌کند و بعد redirect می‌دهد. به همین دلیل قفلِ روی کارت یک کنترل واقعی است، نه
یک دکمهٔ مخفی.

چند تصمیم که آگاهانه گرفته شده‌اند:

- **Repository جنریک وجود ندارد.** `DbSet<T>` خودش یک repository است؛ پوشاندن آن فقط کیفیت
  Query را پایین می‌آورد. لایهٔ Application مستقیماً روی `ISentinelDbContext` کوئری می‌نویسد و
  هرجا کوئری پیچیده شد، به یک Query Service نام‌دار تبدیل می‌شود.
- **Business logic داخل Controller نیست.** برای نمونه کل تصمیم ورود در `PortalSignInService`
  است، نه در `AccountController`.
- **هیچ‌جا `DateTimeOffset.UtcNow` صدا زده نمی‌شود.** همه‌جا `TimeProvider` تزریق می‌شود تا
  منطق انقضا و Grace Period قابل تست باشد.
- **وابستگی به دیتابیس خاص حداقل است.** فقط `AddSentinelPersistence` می‌داند کدام موتور فعال
  است؛ پیکربندی موجودیت‌ها از نوع ستون provider-specific استفاده نمی‌کند.

## اجرای سریع محلی

سریع‌ترین مسیر: SQLite، بدون نیاز به هیچ سرور دیتابیسی.

نخست اولین ادمین را از طریق user-secrets تعریف کنید (رمز هرگز داخل فایل‌های پروژه نوشته
نمی‌شود):

```bash
cd src/Sentinel.Web
dotnet user-secrets set "Seed:SuperAdmin:Enabled" "true"
dotnet user-secrets set "Seed:SuperAdmin:UserName" "admin"
dotnet user-secrets set "Seed:SuperAdmin:Email" "admin@example.com"
dotnet user-secrets set "Seed:SuperAdmin:Password" "<یک رمز حداقل ۱۲ کاراکتری>"
```

سپس اجرا کنید:

```bash
dotnet run --project src/Sentinel.Web
```

پرتال روی `https://localhost:7238` بالا می‌آید. پروفایل `http` برای اجرای بدون TLS:

```bash
dotnet run --project src/Sentinel.Web --launch-profile http
```

### حساب‌های نمونهٔ توسعه

وقتی `Seed:IncludeSampleApplications` روشن است (که در `appsettings.Development.json` هست)، این
حساب‌ها هم ساخته می‌شوند تا هر حالت پرتال بدون دست‌کاری دیتابیس قابل‌دیدن باشد. رمز همهٔ آن‌ها
مقدار `Seed:SampleMemberPassword` است.

| نام کاربری | شماره تلفن | چه چیزی را نشان می‌دهد |
|---|---|---|
| `member.active` | 09120000001 | عضو سالم Pro؛ همه‌چیز تا سطح Pro باز است |
| `member.basic` | 09120000002 | سطح Basic؛ کارت قفل‌شده به‌خاطر `MinimumTier` |
| `member.expiring` | 09120000003 | دو روز مانده؛ هشدار تمدید روی داشبورد |
| `member.grace` | 09120000004 | دیروز تمام شده؛ در مهلت تمدید، دسترسی برقرار |
| `member.expired` | 09120000005 | خیلی گذشته از مهلت؛ همهٔ کارت‌های مبتنی بر عضویت قفل |
| `member.suspended` | 09120000006 | عضویت معتبر ولی حساب مسدود؛ خودِ ورود رد می‌شود |
| `member.nomembership` | 09120000007 | اصلاً عضویتی ندارد؛ حالت خالی صفحهٔ عضویت |

با هر سه شکل می‌توان وارد شد: نام کاربری، ایمیل (`member.active@example.com`) یا شماره تلفن —
و شماره را می‌توانید `09120000001`، `+989120000001` یا با ارقام فارسی `۰۹۱۲۰۰۰۰۰۰۱` بنویسید.

این حساب‌ها هرگز در Production ساخته نمی‌شوند: `IncludeSampleApplications` آنجا با خطای
startup رد می‌شود.

پس از نخستین ورود، `Seed:SuperAdmin:Enabled` را `false` کنید و رمز را از secret store پاک
کنید:

```bash
dotnet user-secrets remove "Seed:SuperAdmin:Password" --project src/Sentinel.Web
```

## اجرا با Docker

```bash
cp .env.example .env
```

`.env` را پر کنید (دست‌کم `POSTGRES_PASSWORD`، و برای نخستین اجرا مقادیر `SEED_SUPERADMIN_*`)،
سپس:

```bash
docker compose up --build
```

نکات مهم برای Production:

- `sentinel-keys` را حتماً به‌صورت volume نگه دارید؛ در غیر این صورت هر redeploy کلیدهای
  Data Protection را از بین می‌برد و همهٔ کاربران از حساب خارج می‌شوند.
- `FORWARDED_HEADER_HOPS` را فقط وقتی بزرگ‌تر از صفر بگذارید که یک reverse proxy تحت کنترل
  خودتان تنها راه ورود باشد.
- پس از ساخت اولین ادمین، `SEED_SUPERADMIN_*` را خالی کنید و دوباره deploy کنید.

## دیتابیس و Migration

Migrationهای موجود در این مخزن برای **PostgreSQL** تولید شده‌اند.

| Provider | نحوهٔ ساخت schema | کاربرد |
|---|---|---|
| `PostgreSql` | Migration (`Database:MigrateOnStartup` یا دستور جداگانه) | Production |
| `Sqlite` | `EnsureCreated` از روی مدل | توسعهٔ محلی و تست |
| `SqlServer` | Migration اختصاصی خودتان | پشتیبانی‌شده، ولی migration همراه ندارد |

ساخت migration جدید:

```bash
dotnet ef migrations add <Name> --project src/Sentinel.Infrastructure --output-dir Persistence/Migrations
```

اعمال migrationها روی یک دیتابیس واقعی:

```bash
SENTINEL_MIGRATIONS_CONNECTION="Host=localhost;Database=sentinel;Username=sentinel;Password=..." \
  dotnet ef database update --project src/Sentinel.Infrastructure
```

تولید اسکریپت SQL برای اعمال دستی (روش پیشنهادی برای Production):

```bash
dotnet ef migrations script --project src/Sentinel.Infrastructure --idempotent -o migrate.sql
```

### اگر SQL Server می‌خواهید

`Database:Provider` را `SqlServer` بگذارید و یک مجموعه migration مخصوص خودش بسازید. چون
EF نمی‌تواند دو مجموعه migration را در یک اسمبلی از هم تفکیک کند، این کار به یک پروژهٔ
migration جداگانه با `MigrationsAssembly` نیاز دارد. تا آن زمان `MigrateOnStartup` برای
SQL Server عمداً با پیام صریح خطا رد می‌شود تا DDL مخصوص Postgres روی SQL Server اجرا نشود.

## فرانت‌اند

Vue به‌صورت SPA استفاده نمی‌شود. Routing، render و SEO با ASP.NET Core MVC است و هر صفحه
می‌تواند جزیرهٔ Vue کوچک خودش را داشته باشد.

```bash
cd src/Sentinel.Web
npm install
npm run build      # یک‌بار
npm run watch      # هنگام توسعه
```

خروجی در `wwwroot/js/dist/` می‌نشیند و کامیت می‌شود.

**چرا build step وجود دارد؟** نسخهٔ کاملِ مرورگری Vue برای کامپایل template از `new Function`
استفاده می‌کند و اجرای آن نیازمند `unsafe-eval` در CSP است — که عملاً بیشتر فایدهٔ CSP را از
بین می‌برد. با Vite، templateها در زمان build کامپایل می‌شوند و runtime-only build بارگذاری
می‌شود؛ به همین دلیل CSP این پروژه نه `unsafe-eval` دارد و نه `unsafe-inline` برای script.

صفحهٔ ورود عمداً بدون Vue است: این تنها صفحه‌ای است که باید حتی با JavaScript خاموش هم کار کند،
پس Razor فرم واقعی را render می‌کند و JS ساده فقط قابلیت‌های اضافه (نمایش رمز، هشدار Caps Lock،
جلوگیری از ارسال دوباره) را می‌افزاید.

جزیره‌های فعلی Vue:

| جزیره | صفحه | چرا Vue |
|---|---|---|
| `AppGrid` | برنامه‌های من | جست‌وجو و فیلتر، وضعیت واقعی سمت کلاینت |
| `AppCard` | برنامه‌های من + داشبورد | یک پیاده‌سازی کارت برای هر دو صفحه |

داده از یک attribute به‌نام `data-apps` خوانده می‌شود، نه از `<script type="application/json">`.
دلیلش مشخص است: Razor مقدار attribute را encode می‌کند و `dataset` آن را decode می‌کند، پس داده
تحت هیچ شرایطی نمی‌تواند از context خودش بیرون بزند — در حالی که بلوک inline به `@Html.Raw` و
قواعد escape جداگانه نیاز داشت. در کل پروژه حتی یک `Html.Raw` وجود ندارد.

تمام رشته‌هایی که جزیره render می‌کند از سرور و از پیش ترجمه‌شده می‌رسند، بنابراین فقط یک
catalogue ترجمه وجود دارد و هیچ منطق زبانی داخل JS نیست. هر صفحه‌ای که جزیره دارد، یک
`<noscript>` با فهرست ساده و کاملاً کارآمد هم دارد.

## پیکربندی

`src/Sentinel.Web/appsettings.Example.json` تمام کلیدها را با توضیح فهرست کرده است. متغیرهای
محیطی با دو زیرخط تودرتو می‌شوند:

```bash
Database__Provider=PostgreSql
ConnectionStrings__Sentinel="Host=db;Database=sentinel;Username=sentinel;Password=..."
Seed__SuperAdmin__Password="..."
```

مهم‌ترین کلیدها:

| کلید | پیش‌فرض | توضیح |
|---|---|---|
| `Database:Provider` | `PostgreSql` | `PostgreSql` \| `Sqlite` \| `SqlServer` |
| `Database:MigrateOnStartup` | `false` | برای چند replica خاموش بماند |
| `Security:RequireHttps` | `true` | HSTS، ریدایرکت HTTPS و کوکی با پیشوند `__Host-` |
| `Security:SessionLifetimeMinutes` | `480` | طول عمر نشست |
| `Security:ForwardedHeaderHops` | `0` | تعداد proxyهای مورد اعتماد |
| `Security:Password:MinimumLength` | `12` | حداقل طول رمز |
| `Security:Lockout:MaxFailedAttempts` | `5` | قفل موقت حساب |
| `Security:LoginRateLimit:PermitLimit` | `10` | سقف تلاش ورود در هر پنجره، به ازای هر IP |
| `Membership:GracePeriodDays` | `3` | مهلت پس از انقضا |
| `Telegram:Enabled` | `false` | کل یکپارچگی تلگرام؛ خاموش یعنی اعلان‌ها فقط در پرتال |
| `Telegram:BotToken` | خالی | فقط از متغیر محیطی؛ یک credential کامل است |
| `Telegram:BotUsername` | خالی | بدون @، برای ساخت لینک `t.me` |
| `Telegram:PublicBaseUrl` | خالی | مبدأ عمومی پرتال، تا لینک اعلان‌ها در تلگرام کار کند |
| `MediaStorage:RootPath` | `media` | محل ذخیرهٔ آیکون‌ها؛ باید بیرون از wwwroot باشد |
| `MediaStorage:MaxIconBytes` | `524288` | سقف حجم هر آیکون |
| `DataProtection:KeyRingPath` | خالی | مسیر نگهداری کلیدهای رمزنگاری کوکی |

### محتوای محصول و مستندات

بدنهٔ متنی محصول‌ها و مقالات با یک **زیرمجموعهٔ محدود از نشانه‌گذاری** نوشته می‌شود، نه HTML.
`RichTextRenderer` **پاک‌کنندهٔ HTML نیست و عمداً نیست**: ورودی *اول* به‌طور کامل encode می‌شود،
پس هیچ `<` نوشتهٔ کاربر زنده نمی‌ماند، و تنها تگ‌هایی در خروجی هستند که خودِ همین فایل ساخته است.
یک sanitizer باید HTML مهاجم را parse کند و تصمیم بگیرد کدام بخش بی‌خطر است — بازی‌ای که هر
ویژگی عجیب parser و هر ترفند mutation-XSS یک شانس برای اشتباه است. اینجا چیزی برای اشتباه کردن
وجود ندارد، چون هیچ تگی از کاربر نگه داشته نمی‌شود.

رندر **یک بار در زمان ذخیره** انجام می‌شود، نه در هر نمایش. بنابراین مسیر خواندنی که رندر را
فراموش کند فقط چیزی نشان نمی‌دهد، نه این‌که HTML خام به مرورگر بفرستد. `Html.Raw` در تمام پروژه
فقط **یک** جا استفاده می‌شود (`_RenderedContent.cshtml`) و یک تست این را تضمین می‌کند.

هر بخش محتوا یک مخاطب دارد: `Public` (هر کسی که محصول را می‌بیند — مخاطب پیش از خرید)،
`Entitled` (فقط دسترسی فعال)، `Internal` (فقط گردانندگان). این تصمیم در `ContentAudience`
گرفته می‌شود، نه در view، و از همان پاسخ `ProductAccessRules` تغذیه می‌شود.

### ماژول VPN

ماژول VPN یک **اسمبلی جداگانه** است (`src/Sentinel.Vpn`). سیاست آن با هر محصول دیگری فرق دارد —
ظرفیت، provisioning روی پنل شخص ثالث، سهمیهٔ ترافیک، جابه‌جایی بین کشورها — و جدا بودنش یعنی
هیچ‌کدام از این‌ها به کاتالوگ مشترک نشت نمی‌کند. وابستگی فقط رو به داخل است:
`Sentinel.Application` چیزی از این پروژه نمی‌داند.

موجودیت‌ها در همان DbContext مشترک ثبت می‌شوند (نه یک context دوم) تا provisioning و بعدها کیف
پول بتوانند در **یک تراکنش** commit شوند؛ جدایی‌ای که مهم است جدایی کد و سیاست است، نه دیتابیس.
ماژول دسترسی خود را با یک اینترفیس باریک `IVpnDbContext` می‌گیرد، نه با یک `Set<T>()` عمومی.

**احراز هویت 3x-ui:** نسخهٔ ۳ یک **توکن ثابت** در `Settings → Security → API Token` می‌سازد که
به‌صورت `Authorization: Bearer` فرستاده می‌شود. نه login رفت‌وبرگشتی، نه session cookie‌ای که باید
زنده نگه داشته شود. توکن با key ring دادهٔ برنامه رمز می‌شود، هرگز لاگ نمی‌شود و پس از ذخیره
**دیگر هرگز کامل نمایش داده نمی‌شود** — فقط چهار کاراکتر آخرش.

کلاینت‌ها روی پنل با **ایمیل** آدرس می‌شوند (کلید طبیعی خود پنل در نسخهٔ ۳). پرتال یک شناسهٔ
مبهم می‌سازد (`s-<16 hex>`) و هرگز ایمیل واقعی مشتری را به سیستم شخص ثالث نمی‌دهد. **هیچ
UUID، رمز یا پروتکلی فرستاده نمی‌شود**: پنل خودش هر secret مخصوص پروتکل را می‌سازد، پس پرتال
هرگز credential مشتری را در دست ندارد و هرگز نمی‌تواند منبع یک credential ضعیف باشد.

سه دام واقعی که در کلاینت مدیریت شده‌اند:

- `totalGB` نامش گیگابایت است ولی واحدش **بایت** است؛ `expiryTime` **میلی‌ثانیهٔ epoch** است.
- `update/{email}` ردیف را **جایگزین** می‌کند نه patch؛ ارسال ناقص، فیلدهای دیگر را پاک می‌کند.
- `attach`/`detach` وجود دارند، پس جابه‌جایی سرویس = attach در مقصد → تأیید → detach در مبدأ؛
  حذف‌و‌ساخت‌مجدد پنجره‌ای بدون هیچ کانفیگ کارآمد باقی می‌گذاشت.

**`UnknownOutcome`** مهم‌ترین بخش قرارداد است. timeout یا قطع اتصال روی یک **نوشتن** یعنی
نمی‌دانیم پنل آن را اعمال کرده یا نه — و کار غلط، retry است، چون تلاش اول ممکن است موفق شده
باشد. این یک outcome مستقل است تا هیچ فراخوانی‌کننده‌ای نتواند تصادفاً آن را «خطا» بخواند.
در مقابل، آدرس مسدود (`Blocked`) قطعی و بی‌خطر است، چون هیچ‌چیز از پروسه بیرون نرفته.

### Feature Flag‌ها

بخش `Features` هر ناحیه از پرتال را جداگانه روشن و خاموش می‌کند. **خاموش‌کردن یک قابلیت،
endpointهای سمت سرور را هم می‌بندد، نه فقط لینک منو را.** پاسخ عمداً `404` است و نه `403`:
قابلیتی که خاموش است باید از قابلیتی که اصلاً ساخته نشده قابل‌تشخیص نباشد، وگرنه پاسخ سرور
خودش نقشه‌ای از بخش‌های منتشرنشده می‌شود.

| کلید | پیش‌فرض | توضیح |
|---|---|---|
| `Features:ProductLibraryEnabled` | `true` | کل کتابخانهٔ محصولات |
| `Features:ProductDiscoveryEnabled` | `true` | خاموش یعنی پرتال فقط دعوت‌محور: «کتابخانهٔ من» می‌ماند، «کشف محصولات» بسته می‌شود |
| `Features:ProductDocumentationEnabled` | `true` | مستندات محصول |
| `Features:BetaProductsEnabled` | `true` | خاموش یعنی محصولات پیش‌انتشار از کاتالوگ برداشته می‌شوند؛ کسی که قبلاً دعوت شده دسترسی‌اش را از دست نمی‌دهد |
| `Features:ExternalSubscriptionsEnabled` | `true` | افزودن لینک اشتراک بیرونی توسط کاربر |
| `Features:VpnSelfServiceEnabled` | **`false`** | مدیریت سرویس VPN توسط خود کاربر |
| `Features:PurchasesEnabled` | **`false`** | سفارش پلن |
| `Features:PaymentsEnabled` | **`false`** | هر مسیر پرداخت آنلاین |
| `Features:WalletEnabled` | **`false`** | کیف پول و دفتر اعتبار |

چهار کلید آخر عمداً پیش‌فرض `false` دارند و **تا انجام یک بازبینی امنیتی جداگانه نباید در
Production روشن شوند**. نام ناشناخته هم خاموش تلقی می‌شود (fail closed)، تا یک غلط املایی یا
یک کلید تغییرنام‌یافته چیزی را بی‌صدا باز نگذارد.

هیچ secret‌ای در فایل‌های مخزن نیست. در توسعه از `dotnet user-secrets` و در Production از
متغیر محیطی یا secret store استفاده کنید.

چند تنظیم در Production عمداً باعث **خطای startup** می‌شوند (نه هشدار):
`Database:EnableSensitiveDataLogging`، `Security:RequireHttps=false`، `Database:Provider=Sqlite`
و `Seed:IncludeSampleApplications`.

| Session | نشست سمت سرور در جدول `UserSessions`؛ خروج، ردیف را باطل می‌کند تا کوکی سرقت‌شده بلافاصله بی‌اثر شود |

| Authorization | Policy-based؛ `FallbackPolicy` یعنی هر endpointی که فراموش شود همچنان بسته است؛ `AllowAnonymous` فقط روی اکشن، نه Controller |

| Headers | HSTS، `X-Content-Type-Options`، `Referrer-Policy`، `Permissions-Policy`، `frame-ancestors`، COOP/CORP؛ حذف `Server` |

| Error Handling | در Production فقط صفحهٔ عمومی + Correlation ID؛ جزئیات فقط در لاگ |
| Secrets | هیچ رمز/توکنی در سورس، لاگ یا Audit نوشته نمی‌شود |

## وضعیت فعلی

**فاز ۱ کامل است:** دامنه، persistence، Identity، نشست‌های سمت سرور، میان‌افزارهای امنیتی،
Rate Limit، Audit، محلی‌سازی fa/en، تم روشن/تیره/خودکار، صفحهٔ ورود، صفحات خطا، Health Check،
Migration اولیهٔ Postgres و Docker.

**فاز ۲ کامل است:** `MembershipStatusResolver`، `AccessRuleEvaluator`، `AccessDecisionService`،
endpoint اجرای برنامه با ثبت Audit، سیاست اعتبارسنجی URL، داشبورد کامل، صفحهٔ برنامه‌های من با
جزیرهٔ Vue، و صفحهٔ عضویت.

**فاز ۳ کامل است:** بخش مدیریت (Area) با فهرست کاربران و صفحه‌بندی/جست‌وجو/مرتب‌سازی سمت سرور،
صفحهٔ جزئیات کاربر، ساخت کاربر، تغییر وضعیت حساب با ابطال فوری نشست‌ها، مدیریت نقش‌ها، ویرایش
عضویت با کنترل هم‌زمانی و پیش‌نمایش زندهٔ وضعیت، ورود با شماره تلفن، و حساب‌های نمونهٔ توسعه.

**فاز ۴ کامل است:** مدیریت کاتالوگ برنامه‌ها، آپلود آیکون با تشخیص نوع از روی بایت‌ها و
ذخیره‌سازی بیرون از wwwroot، اعتبارسنجی آدرس ورود در زمان ذخیره، و اعطا/لغو دسترسی اختصاصی.

**فاز ۵ کامل است:** پروفایل و تغییر رمز عبور، مدیریت نشست‌های فعال، تاریخچهٔ فعالیت،
نمایشگر Audit Log با فیلتر و صفحه‌بندی، صفحهٔ وضعیت سیستم و نقش‌ها، و CI.

**فاز ۶ کامل است:** اتصال حساب به تلگرام با توکن یک‌بارمصرف، سیستم اعلان با الگوی outbox،
صفحهٔ اعلان‌ها با نشانگر خوانده‌نشده، ارسال پیام به یک کاربر یا همگانی از پنل مدیر، و اعلان
خودکار روی رویدادهایی مثل اعطای دسترسی.

**فاز ۷ کامل است:** کانفیگ‌ها — دریافت لینک اشتراک از سمت سرور با محافظت SSRF، parse کردن
`vless/vmess/trojan/ss/hysteria2/tuic`، نمایش هر سرور به‌صورت کارت کوچک با دکمهٔ کپی، نوار حجم
و انقضا از هدر `subscription-userinfo`، و پاک‌سازی اشتراک‌های تمام‌شده از پنل مدیر.

**هشدار خودکار انقضا اضافه شد:** یک سرویس زمان‌بندی‌شده که عضویت‌ها و اشتراک‌های رو به پایان،
در مهلت تمدید، منقضی، یا با حجم تمام‌شده را پیدا می‌کند و به صاحبشان اطلاع می‌دهد.

**۶۰۹ تست سبز** (۳۷۱ unit + ۲۳۸ integration).

### هشدار انقضا

تایمر بخش ساده‌اش بود. دو چیز این job را غیرپیش‌پاافتاده می‌کند:

**«یک‌بار در هر مرحله»، نه «یک‌بار در هر sweep».** هر عضویت و هر اشتراک، مرحله‌ای را که آخرین
بار در موردش حرف زده شده ذخیره می‌کند (`LastNoticeStage`)، و پیام فقط وقتی می‌رود که مرحله
**بالاتر** برود. یعنی sweep ساعتی روی یک عضویتِ رو به پایان، یک پیام می‌فرستد نه بیست‌وچهار
پیام در روز. مسیر کامل — سالم ← شمارش معکوس ← مهلت تمدید ← منقضی — دقیقاً سه پیام تولید می‌کند.

**تمدید، هشدارها را دوباره مسلح می‌کند.** وقتی مرحله پایین می‌آید (یعنی کاربر تمدید کرده)،
چیزی گفته نمی‌شود ولی مقدار ذخیره‌شده هم پایین می‌آید. بدون این، عضویتی که یک‌بار منقضی و بعد
تمدید شده، دفعهٔ بعد **هرگز** هشدار نمی‌داد.

**روی همهٔ replicaها اجرا می‌شود.** مارکر مرحله روی ردیفی نشسته که concurrency token دارد، پس
اگر دو نمونه هم‌زمان به یک مورد برسند، یکی نوشتنش را می‌بازد و چیزی نمی‌فرستد.

متن پیام به **زبان خود گیرنده** نوشته می‌شود، نه culture محیطیِ thread. یک sweep پس‌زمینه‌ای
request ندارد که culture را از آن به ارث ببرد، پس `INotificationLocalizer` زبان را صریح
می‌گیرد. (همین باعث شد پیام‌های «دسترسی جدید» و «تلگرام متصل شد» هم که قبلاً انگلیسی
hard-code شده بودند، به همین مکانیزم منتقل شوند.)

### کانفیگ‌ها و SSRF

این تنها جایی است که سرور یک URL انتخاب‌شده توسط کاربر را fetch می‌کند، یعنی می‌تواند به پروکسیِ
هرچه در دسترسش هست تبدیل شود — دیتابیس روی شبکهٔ داخلی، کانتینر بغلی، و مهم‌تر از همه
`169.254.169.254` که روی اکثر ابرها credential نمونه را به هرکسی که بپرسد می‌دهد.

سه لایه، و لایهٔ دوم مهم‌ترین است:

1. **URL نوشته‌شده غربال می‌شود** — فقط http/https، بدون credential در URL، پورت از فهرست مجاز،
   و رد کردن نام‌های آشکار داخلی.
2. **هر اتصال TCP، نام میزبان را resolve می‌کند، آدرس‌ها را اعتبارسنجی می‌کند و بعد به یک آدرسِ
   اعتبارسنجی‌شده وصل می‌شود.** بررسی نام میزبان و سپردن resolve دوباره به stack، پنجره‌ای باز
   می‌گذارد که DNS بار دوم جواب دیگری بدهد — همان حملهٔ rebinding. وصل شدن به آدرسی که واقعاً
   بررسی شد این پنجره را می‌بندد. **اگر حتی یکی** از آدرس‌های برگشتی داخلی باشد، کل اتصال رد
   می‌شود.
3. **Redirectها دستی دنبال می‌شوند** تا هر hop از همان غربال رد شود، و بدنه از یک سقف بایت
   سخت‌گیرانه خوانده می‌شود.

`::ffff:169.254.169.254`، `2002::/16` (6to4) و `64:ff9b::/96` (NAT64) هم بسته‌اند — هر سه راه
شناخته‌شدهٔ پوشاندن یک آدرس داخلی در لباس IPv6.

**کانفیگ‌های parse‌شده ذخیره نمی‌شوند.** فقط در حافظه cache می‌شوند و در صورت کهنه شدن دوباره
گرفته می‌شوند، تا credentialهای پروکسی کاربر در دیتابیس ما فقط در یک جا باشند نه دو جا. آنچه
ذخیره می‌شود متادیتاست: حجم، انقضا، تعداد سرور، و وضعیت آخرین fetch — همان چیزی که پنل مدیر
برای تشخیص اشتراک مرده لازم دارد بدون این‌که چیزی fetch کند.

**لینک اشتراک هرگز رندر نمی‌شود** — نه در صفحهٔ کاربر و نه در پنل مدیر. آن لینک خودش credential
است و برای تصمیم‌گیری دربارهٔ مرده بودن یک اشتراک، خواندنش لازم نیست.

### تلگرام و اعلان‌ها

اعلان اول در دیتابیس نوشته می‌شود و بعد از روی همان ردیف به تلگرام تحویل داده می‌شود — الگوی
**outbox**. سه دلیل: ساخت اعلان نباید پشت API شخص ثالث بلوکه شود، پیام همگانی باید pace شود
وگرنه تلگرام ربات را throttle می‌کند، و ارسال ناموفق باید بدون اجرای دوبارهٔ عملیاتِ مبدأ قابل
retry باشد. نسخهٔ داخل پرتال مرجع است: اگر تلگرام هرگز کار نکند، کاربر همچنان پیام را دارد.

**توکن اتصال فقط به‌صورت hash ذخیره می‌شود.** توکن از سرورهای تلگرام رد می‌شود و در تاریخچهٔ
چت می‌نشیند، پس مثل هر credential در حال انتقال با آن رفتار شده: ۲۵۶ بیت تصادفی، ده دقیقه
عمر، یک‌بارمصرف، و صدور توکن تازه توکن قبلی را باطل می‌کند. پاسخ ربات برای توکن ناشناخته،
مصرف‌شده و منقضی **یکسان** است — تفکیک آن‌ها یعنی تأیید این‌که توکنی زمانی واقعی بوده.

با `Telegram:Enabled=false` کل قابلیت خواب است: نه polling، نه حلقهٔ تحویل، و پرتال اصلاً
پیشنهاد اتصال نمی‌دهد. اعلان‌ها همچنان نوشته و خوانده می‌شوند.

### CI

سه job در `.github/workflows/ci.yml`:

- **build-and-test** — restore، رد کردن build در صورت وجود پکیج آسیب‌پذیر، ساخت فرانت‌اند، و
  بررسی این‌که bundleهای کامیت‌شده با سورس هم‌خوان‌اند (اگر `npm run build` خروجی متفاوتی بدهد
  یعنی کامیت کهنه است)، سپس build و test در حالت Release.
- **migrations** — یک PostgreSQL واقعی بالا می‌آید و migrationها روی آن اعمال می‌شوند، دو بار
  (برای اطمینان از idempotent بودن)، و در آخر `has-pending-model-changes` بررسی می‌کند که مدل
  بدون migration تغییر نکرده باشد. تست‌ها روی SQLite اجرا می‌شوند؛ این job همان چیزی است که
  ثابت می‌کند migrationها روی موتور Production هم کار می‌کنند.
- **docker** — ایمیج Production ساخته می‌شود ولی push نمی‌شود.

### آپلود آیکون

سه لایهٔ مستقل:

1. **نوع فایل از بایت‌ها تعیین می‌شود، نه از نام یا Content-Type.** فایلی به نام `logo.png` که
   خودش را `image/png` معرفی کند ولی محتوایش `<script>` باشد رد می‌شود.
2. **SVG پذیرفته نمی‌شود.** SVG یک سند XML است، می‌تواند `<script>` و ارجاع بیرونی داشته باشد،
   و سرو کردنش از دامنهٔ خودمان یعنی XSS ذخیره‌شده. پشتیبانی امن از آن به یک sanitizer واقعی
   نیاز دارد که تصمیم مستقلی است، نه چیزی که لای فیلد آیکون رد شود.
3. **نام فایل سمت سرور تولید می‌شود** (۳۲ کاراکتر hex + پسوند مجاز). این الگو اصلاً نمی‌تواند
   traversal را بیان کند؛ بررسی محدودهٔ مسیر هم به‌عنوان لایهٔ پشتیبان وجود دارد.

فایل‌ها بیرون از `wwwroot` ذخیره می‌شوند تا هرگز از مسیر static-file سرو نشوند، و فقط از طریق
`/media/app-icon/{key}` با `Content-Type` محاسبه‌شده از پسوندِ تولیدشدهٔ خودمان تحویل داده
می‌شوند. آدرس شامل نسخه‌ای برگرفته از نام فایل است، پس با جایگزینی آیکون، URL عوض می‌شود و
نسخهٔ کش‌شده هرگز کهنه نمی‌ماند.

محدودیت‌های شناخته‌شدهٔ فعلی:

- **تغییر اندازه یا فشرده‌سازی تصویر انجام نمی‌شود.** فایل همان‌طور که آمده ذخیره می‌شود؛
  کنترل واقعی، سقف حجم است. افزودن پردازش تصویر یعنی یک کتابخانهٔ decode روی ورودی نامعتمد،
  که سطح حملهٔ جدیدی باز می‌کند.
- **Audit Log فقط‌خواندنی است و هیچ endpointی برای حذف یا ویرایش آن وجود ندارد** — این عمدی
  است. گزارشی که خودِ اپلیکیشن بتواند بازنویسی‌اش کند، مدرک هیچ‌چیز نیست. یک تست وجودِ چنین
  endpointی را رد می‌کند. در عوض، سیاست نگهداری و آرشیو هنوز پیاده نشده و جدول Audit
  بی‌نهایت رشد می‌کند؛ برای استقرار طولانی‌مدت باید یک job پاک‌سازی اضافه شود.
- **ثبت‌نام خودکار، بازیابی رمز از طریق ایمیل و OTP وجود ندارد.** هیچ transport ایمیل/پیامکی
  در پروژه نیست؛ حساب‌ها را ادمین می‌سازد. معماری برای افزودن این‌ها آماده است.
- **صفحهٔ سیستم فقط‌خواندنی است.** تنظیمات از متغیر محیطی و secret store می‌آیند؛ صفحه‌ای که
  آن‌ها را بازنویسی کند یعنی یک منبع حقیقتِ دومِ قابل‌تغییر برای مقادیر امنیتی.
- **هشدار انقضای اشتراک به fetch وابسته است.** حجم و تاریخ انقضا فقط وقتی تازه می‌شود که کسی
  صفحهٔ کانفیگ‌ها را باز کند، پس برای کاربری که مدت‌هاست وارد نشده، sweep روی دادهٔ کهنه کار
  می‌کند. افزودن یک refresh دوره‌ای به همان sweep کار کوچکی است، ولی هر عضو را به یک درخواست
  خروجی دوره‌ای تبدیل می‌کند و عمداً انجام نشده.
- برای **SQL Server** مجموعه migration همراه پروژه نیست (بالا توضیح داده شد).
- اعتبارسنجی نشست در هر درخواست یک lookup روی کلید اصلی می‌زند و عمداً cache نمی‌شود، تا
  ابطال نشست بلافاصله و روی همهٔ replicaها اثر کند.
- `Seed:IncludeSampleApplications` علاوه بر برنامه‌های نمونه، به هر حسابی که عضویت ندارد یک
  عضویت فعال می‌دهد تا پرتال روی دیتابیس تازه قابل‌مشاهده باشد. این رفتار در Production با
  خطای startup رد می‌شود.
